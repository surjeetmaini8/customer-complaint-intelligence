# Customer Complaint Intelligence & Root-Cause Analysis

A local ML/NLP project for turning customer complaints into structured analysis. The pipeline classifies complaints, scores severity, finds similar cases, groups related complaints, detects spikes, retrieves relevant knowledge-base documents, and can produce a root-cause summary.

> **Demo data only:** all complaints are synthetic and are generated by `src/ingestion/generators.py`. The documents under `data/knowledge_base/` are also fictional. Nothing in this repository should be treated as real customer or internal company data.

## What the project does

For each complaint, the pipeline can produce:

- category and subcategory with confidence
- sentiment and emotion
- domain-specific entities such as order IDs, amounts and payment methods
- a severity level with the factors behind the score
- similar historical complaints
- cluster membership
- emerging-issue/anomaly signals
- retrieved knowledge-base evidence
- an optional root-cause analysis and recommended actions

The system is designed to work locally first. Lightweight models are used by default, while transformer and LLM paths are optional.

## Main features

- Synthetic complaint generator with 10,000+ records, class imbalance and two injected incidents.
- TF-IDF + Logistic Regression classification, with an optional transformer implementation.
- Rule/lexicon-based sentiment and emotion analysis with optional transformer replacements.
- Regex/rule-based NER with optional spaCy entities.
- Rule-based severity scoring, with an optional XGBoost model.
- FAISS similarity search and HDBSCAN/KMeans clustering.
- Rolling-baseline anomaly detection.
- RAG over the synthetic knowledge base.
- Evidence-ID validation so the LLM cannot return document IDs that were not retrieved.
- Human-review flags for low-confidence predictions.
- FastAPI API and Streamlit dashboard backed by the same SQLite database.
- Feedback storage for later model improvement.

## Installation

```bash
git clone <this project>
cd customer-complaint-intelligence
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Before running the full pipeline, check the environment:

```bash
python scripts/check_environment.py
```

The script reports required dependencies separately from optional packages such as Transformers, PyTorch, sentence-transformers and spaCy.

## Generate data

```bash
python scripts/generate_data.py
python scripts/generate_data.py --n 5000
```

The generator creates complaints across six sources, ten categories and more than forty subcategories. It also adds temporal patterns and two known incidents so the anomaly detector has something measurable to find.

## Train models

```bash
python scripts/train_models.py
```

This trains the category classifier, available per-category subcategory classifiers, and the optional severity model. Metrics are written to `models/training_metrics.json`.

The synthetic dataset is deliberately easy to classify compared with real customer text. For that reason, do not interpret the high accuracy as real-world performance. Macro F1 and the per-class report are more useful when looking at the minority classes. With very small datasets, some subcategory models may be skipped because there are not enough examples per class; inference then returns a low-confidence fallback and marks the result for human review.

To try the optional transformer classifier:

```bash
python scripts/train_models.py --transformer
```

## Run the complete pipeline

For a normal demo run:

```bash
python scripts/run_pipeline.py
```

For a smaller development run:

```bash
python scripts/run_pipeline.py --n 1000 --limit 1000
```

The command runs:

```text
generate data -> train models -> build FAISS indexes -> process complaints
```

The pipeline uses model predictions rather than the generator's ground-truth labels when writing analysis results. LLM root-cause calls are made for representative clusters/issues instead of every complaint.

## API protection

The API-key check is disabled by default for local development. To enable it, set:

```env
API_REQUIRE_KEY=true
API_KEY=replace-with-a-long-random-value
```

Clients then send `X-API-Key`. Do not expose the demo API to the public internet without authentication, TLS, rate limiting and proper deployment controls.

## LLM configuration

Set these values in `.env` if you want live LLM calls:

```env
LLM_API_KEY=...
LLM_MODEL=gpt-4o-mini
LLM_BASE_URL=https://api.openai.com/v1
```

Without an API key, the project uses a deterministic mock path based on retrieved knowledge-base content. Responses are labeled with `llm_mode: "mock"`; the fallback is not presented as a real generative model.

The LLM receives masked complaint text. Evidence IDs are validated after generation, and unsupported IDs are removed. This reduces citation errors but does not guarantee that a model interprets the retrieved document correctly. Human review is still needed for important decisions.

## Privacy note

The repository uses synthetic data, so the demo keeps the original complaint text by default for dashboard inspection. For real customer data, set:

```env
RETAIN_ORIGINAL_TEXT=false
```

A production deployment would also need encryption, access controls, retention/deletion policies, audit logging and stricter API responses. Regex-based PII detection is useful as a local baseline but is not a complete privacy solution.

## Evaluation

Classification uses a stratified train/test split and reports:

- accuracy
- macro precision/recall/F1
- weighted precision/recall/F1
- per-class metrics
- confusion matrix

The anomaly detector is checked against the two injected incidents. RAG retrieval can be tested with domain-specific queries such as `OTP never arrives`. No evaluation numbers are hardcoded; metrics are generated from the current run.

## Limitations

This is a demo/research project rather than a production customer-support system. Important limitations include:

- the complaint data is synthetic and relatively clean
- lightweight sentiment/emotion/NER models will struggle with noisy real-world language
- regex PII detection can miss unusual formats
- the mock LLM is template-based
- SQLite is suitable for the demo but not a high-scale production store
- API authentication is optional and disabled by default
- there is no production-grade authorization or rate limiting
- model and index artifacts are generated locally and should be rebuilt when the data changes

## Tests

Run the unit tests with:

```bash
pytest -q
```

The tests cover core PII masking, repository filtering/count consistency and the low-confidence subcategory fallback. Add integration tests after installing the full dependency set if you want to validate the complete API and FAISS pipeline in CI.

## Design choices

The project intentionally uses simple local models for tasks that do not need an LLM. More expensive reasoning is reserved for issue/cluster analysis. Optional heavy dependencies can be enabled without changing the interfaces used by the rest of the pipeline.

The main goal is a working, inspectable implementation rather than an architecture that is complicated for its own sake.
